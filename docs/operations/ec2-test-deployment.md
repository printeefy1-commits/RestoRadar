# نشر نسخة اختبار على AWS EC2

هذه التعليمات تنشر التطبيق المحلي الحالي على خادم واحد لتجربة الواجهات والجلسات والمهام. لا تمثل تنفيذ السحابة الهجينة أو رصد الكاميرات الحية. بعد تشغيل الأساس، تتوفر [إضافة اختيارية لتجربة فيديو مسجل على CPU](recorded-video-trial.md)، مع رفع الملف من المتصفح أو استخدام فيديو التجربة الأصلي، دون تعديل الجلسات التشغيلية.

## 1. إنشاء الخادم من AWS Console

1. افتح EC2 في المنطقة المناسبة لك واختر **Launch instance**. سمّه `RestoRadar-test`.
2. اختر صورة **Ubuntu Server 24.04 LTS، x86_64** من الناشر الرسمي Canonical.
3. ابدأ بـ **t3.medium: عدد 2 vCPU و4 GiB RAM**، وقرص **gp3 بسعة 30 GiB**. هذا اقتراح لاختبار التطبيق الحالي والبناء، وليس وعدًا بأداء تحليل الفيديو. لا تحتاج GPU لهذه المرحلة؛ نعيد تقييم العتاد عند إضافة التحليل. هذه الموارد مدفوعة حسب المنطقة ومدة الاستخدام، ولا نفترض أنها مجانية.
4. أنشئ أو اختر Key pair، واحفظ ملف المفتاح الخاص على جهازك الشخصي. لا ترفعه للمستودع أو المحادثة.
5. في Security Group اسمح بـ TCP **22 من عنوان IP الخاص بك فقط**، و**80 و443** للوصول عبر الويب وإصدار شهادة TLS. لا تفتح 3001 أو5173 أو5432. يمكن تقييد وصول HTTPS لاحقًا بعناوين المختبرين؛ يجب أن تبقى آلية تجديد الشهادة قابلة للوصول.
6. شغّل المثيل. يفضل ربط Elastic IP ثم إنشاء سجل DNS من النوع A، مثل `radar.your-domain.com`، يشير إليه. العنوان العام الثابت له رسوم أيضًا. احذف سجل AAAA غير الصحيح إن كان اسم النطاق لا يصل إلى هذا الخادم عبر IPv6.

يلزم اسم نطاق تتحكم به للحصول على HTTPS موثوق مباشرة على هاتف Android. إن لم يوجد نطاق، استخدم مسار النفق الخاص في القسم الأخير بدل تعريض تسجيل الدخول عبر HTTP.

## 2. تثبيت Docker

من **جهازك الشخصي**، اتصل بالخادم، مع استبدال المسار والعنوان:

```bash
chmod 400 /path/to/your-key.pem
ssh -i /path/to/your-key.pem ubuntu@EC2_PUBLIC_IP
```

تحقق من هوية المضيف عند أول اتصال؛ لا تعطل فحص مفتاح SSH. على **EC2** نفّذ:

```bash
sudo apt-get update
sudo apt-get install -y docker.io docker-compose-v2 docker-buildx ca-certificates curl openssl
sudo systemctl enable --now docker
sudo docker compose version
```

هذه الخطوات تستخدم مستودعات Ubuntu الموقعة دون تنزيل سكربت تثبيت عشوائي.

## 3. جلب المشروع مباشرة من GitHub

اختار المالك النشر مباشرة من GitHub بدل نقل الملفات عبر الجهاز الشخصي أو CloudShell/S3. على **طرفية EC2 الحالية** نفّذ:

```bash
sudo apt-get install -y git
cd ~
GIT_TERMINAL_PROMPT=0 git clone https://github.com/printeefy1-commits/RestoRadar.git
cd RestoRadar
git log -1 --oneline
ls infra/ec2
```

إذا كان مجلد `RestoRadar` موجودًا مسبقًا، افحصه قبل أي أمر آخر، ولا تحذفه أو تستبدله. إذا كان نفس المستودع دون تغييرات محلية، استخدم `git pull --ff-only origin main`. لا تستخدم reset أو force لمحو تغييرات قائمة.

إذا فشل الجلب بسبب الصلاحيات، فهذا لا يعني أن المشروع أو Docker معطل. للمستودع الخاص يمكن إعداد Deploy key بصلاحية قراءة فقط على EC2 وإضافة **المفتاح العام** في إعدادات المستودع على GitHub. لا تُرسل مفتاحًا خاصًا أو token في المحادثة، ولا تضع بيانات اعتماد في رابط Git. نختبر الجلب الحالي أولًا قبل إضافة أي اعتماد جديد.

وجود `.env.example` و`infra/ec2/ec2.env.example` مقصود؛ هما قوالب وليسا أسرار النشر. تبقى `infra/ec2/ec2.env` و`.secrets` وDocker volumes محلية خارج Git.

## 4. إعداد النطاق وكلمة مرور قاعدة البيانات

```bash
test -f infra/ec2/ec2.env || cp infra/ec2/ec2.env.example infra/ec2/ec2.env
nano infra/ec2/ec2.env
```

غيّر `APP_DOMAIN` إلى اسم نطاقك دون بروتوكول، و`PUBLIC_ORIGIN` إلى `https://` متبوعًا بنفس النطاق. اترك `ENABLE_SIMULATOR=false` أو فعّله إلى `true` فقط لتجربة الأحداث المصطنعة؛ هذا لا يفعّل تحليل الفيديو.

أنشئ كلمة مرور عشوائية لقاعدة البيانات، مرة واحدة، دون عرضها:

```bash
install -d -m 700 infra/ec2/.secrets
if [ ! -f infra/ec2/.secrets/database_password ]; then
  (umask 077; openssl rand -hex 32 > infra/ec2/.secrets/database_password)
fi
chmod 444 infra/ec2/.secrets/database_password
```

الدليل الخاص بصلاحية 700 يحمي الوصول على المضيف، والملف قابل للقراءة داخل الحاويتين اللتين تحتاجانه. لا تضفه إلى Git أو الحزمة. لا تولّد كلمة مختلفة لقاعدة سبق تهيئتها؛ تغيير ملف السر وحده لا يغيّر كلمة مرور PostgreSQL القائمة.

## 5. تشغيل التطبيق

من جذر المشروع:

```bash
sudo docker compose --env-file infra/ec2/ec2.env -f infra/ec2/compose.yml up -d --build --wait --wait-timeout 180
sudo docker compose --env-file infra/ec2/ec2.env -f infra/ec2/compose.yml ps
```

الخدمات هي PostgreSQL، والتطبيق، وCaddy الذي يصدر شهادة TLS ويوجه الطلبات إلى التطبيق. لا تنشر PostgreSQL أو منفذ التطبيق مباشرة. تعمل الترحيلات عند بدء التطبيق قبل استقباله الطلبات، وتبقى البيانات والشهادات في Docker volumes مستقلة.

تحقق باستخدام نطاقك الفعلي:

```bash
curl --fail --silent --show-error https://YOUR_DOMAIN/api/health
```

النتيجة المتوقعة تتضمن `status: ok` و`mode: LOCAL_ONLY`. كلمة LOCAL_ONLY تعني أن هذا هو خادم التشغيل الحالي دون طبقة المزامنة الهجينة، حتى لو كان مستضافًا على EC2.

إن فشل TLS، راجع DNS وSecurity Group وسجلات Caddy. لا تستخدم `curl -k` أو تعطيل التحقق من الشهادة لحل المشكلة:

```bash
sudo docker compose --env-file infra/ec2/ec2.env -f infra/ec2/compose.yml logs --tail=100 caddy app
```

## 6. إنشاء أول حساب مالك

على EC2، اختر قيمك الخاصة، مع كلمة مرور لا تقل عن 12 حرفًا:

```bash
export RESTAURANT_NAME='اسم المطعم'
export OWNER_NAME='اسم المالك'
export OWNER_EMAIL='your-email@example.com'
read -r -s -p 'كلمة مرور المالك: ' OWNER_PASSWORD
export OWNER_PASSWORD
sudo --preserve-env=RESTAURANT_NAME,OWNER_NAME,OWNER_EMAIL,OWNER_PASSWORD \
  docker compose --env-file infra/ec2/ec2.env -f infra/ec2/compose.yml \
  run --rm --no-deps -e RESTAURANT_NAME -e OWNER_NAME -e OWNER_EMAIL -e OWNER_PASSWORD app setup-owner
unset OWNER_PASSWORD
```

لا توجد بيانات دخول افتراضية، ولا يقبل الأمر تهيئة مطعم ثانٍ فوق تهيئة قائمة. بعد ذلك افتح نطاقك على Android، سجّل الدخول، أدخل مهلات المهام الأربع، وأضف الطاولات والمدير والنادل.

جرّب الاستقبال والتنظيف بالمحاكاة إن فعلتها. أوقف المحاكي عند الانتقال إلى الرصد الحقيقي. راجع أيضًا الإقرارات بين مديرين، وإعادة تعيين مهمة، وبقاء الطاولة غير جاهزة بعد إكمال النادل التنظيف.

## 7. البيانات وإعادة التشغيل

```bash
sudo docker compose --env-file infra/ec2/ec2.env -f infra/ec2/compose.yml restart app
sudo docker compose --env-file infra/ec2/ec2.env -f infra/ec2/compose.yml ps
```

يجب أن تبقى الجلسات والحسابات والمؤقتات محفوظة، وتُسجل فجوة المراقبة عند إعادة التشغيل. ملفات البيانات موجودة على قرص EC2 عبر Docker volumes؛ هذا ليس نسخًا احتياطيًا خارجيًا ولا إعداد توافر عالٍ.

قبل ترقية أو حذف المثيل، أنشئ نسخة قاعدة بيانات محمية واختبر استعادتها في قاعدة منفصلة. لا تستخدم `down -v` أو تحذف volumes أو تعيد توليد سر قاعدة البيانات لإصلاح تعثر نشر قائم. هذه الحزمة مخصصة لاختبار أولي، وليست إجراء ترقية أو استعادة إنتاج معتمدًا.

## 8. الفيديو المسجل في المرحلة التالية

اختار المالك فيديو مسجلًا مصرحًا باستخدامه أولًا. إرسال الفيديو إلى EC2 للاختبار يعني معالجة سحابية لهذا الملف، بينما المعمارية النهائية تعالج الكاميرات داخل المطعم افتراضيًا. تتوفر الآن خدمة اختيارية لتحليل ملف مسجل ورفعه من الموقع وحذفه أو استبداله؛ راجع [دليل تجربة الفيديو](recorded-video-trial.md).

التسليم التالي للرصد الحي يتطلب تقييم النتائج مقابل أوقات جلوس ومغادرة معلّمة يدويًا وربط ملاحظات متحققة بمنطق 5/30 ثانية؛ التجربة المسجلة الحالية لا تنشئ مغادرة أو جلسات حية. لا نعد بعدد تدفقات أو سرعة معالجة قبل القياس. يُحفظ الفيديو المرفوع في تخزين خاص خارج المستودع والصورة حتى يحذفه المالك أو يستبدله.

لا نستخدم كاميرات عُثر عليها في Shodan لمجرد أنها متاحة. عند الانتقال إلى بث حي، نستخدم كاميرا يملكها المطعم أو لديه إذن باختبارها، أو مصدر اختبار منشور لهذا الغرض بشروط تسمح به.

## نتيجة التحقق من حزمة النشر

اختُبرت الحاويات محليًا: بناء الصورة وفحص الأنواع، بدء PostgreSQL والترحيل، تقديم الواجهة وAPI عبر Caddy وHTTPS بشهادة اختبار موثوق بها صراحة، إنشاء المالك وتسجيل دخوله مع Secure/HttpOnly cookies، ثم إعادة تشغيل حاوية التطبيق. بقيت الجلسة وأوقات بدايتها والتصحيح اليدوي محفوظة، وسُجلت فجوة مراقبة ولم تتكرر العملية عند إعادة إرسال معرفها.

نجحت كذلك 23 حالة اختبار منطق، و19 حالة تكامل، واختبارا متصفح. كُشف وأُصلح ترتيب إغلاق اتصالات قاعدة البيانات وحالة إعادة التشغيل قبل أول heartbeat. لم يُنشأ EC2 بعد، ولم تُختبر شهادة اسم نطاق عامة أو هاتف Android فعلي أو أي تحليل فيديو. هذه نتائج الآلة الحالية، وليست تحققًا من نشر AWS.

## اختبار خاص إذا لم يوجد نطاق بعد

يمكن تشغيل Caddy محليًا بشهادة داخلية بدل شهادة عامة:

- في `ec2.env`: اجعل `APP_DOMAIN=localhost` و`PUBLIC_ORIGIN=https://localhost:8443` و`BIND_ADDRESS=127.0.0.1`، مع منافذ المضيف الافتراضية 80 و443.
- من جهازك الشخصي افتح نفقًا: `ssh -i /path/to/your-key.pem -L 8443:127.0.0.1:443 ubuntu@EC2_PUBLIC_IP`.
- استخرج **الشهادة العامة فقط** على EC2 بالأمر التالي ثم انقلها إلى جهازك الشخصي عبر SCP:

```bash
sudo docker compose --env-file infra/ec2/ec2.env -f infra/ec2/compose.yml \
  cp caddy:/data/caddy/pki/authorities/local/root.crt ./restoradar-test-root.crt
```

تحقق على جهازك الشخصي باستخدام `curl --cacert restoradar-test-root.crt https://localhost:8443/api/health`. لتجربة المتصفح يجب الوثوق بهذه الشهادة محليًا لهذا الاختبار بدل تجاهل أخطاء TLS. لا تنقل المفتاح الخاص للـCA. مسار النفق مناسب لاختبار الحاسوب؛ لتجربة Android المباشرة أوصي بالنطاق والشهادة العامة.
